# 장기 개선 과제

아래 항목은 아직 착수하지 않은 구조 개선 후보입니다. 해결 설계안은 확정된
정책이 아니라 구현 전에 현재 도구 동작과 기존 공통 규칙의 충돌 여부를 검증할
초안입니다.

## TASK-01. 장기 작업의 상태 복원 규칙 수립

- **우선순위:** 중.
- **현상:** 프로젝트 진행 기간이 2주를 넘거나 대화 세션이 길어지면 초기 설계
  방향, 과거 합의와 직전 작업 상태를 놓쳐 이미 반려한 구현을 다시 제안한다.
- **원인 가설:** 대화 기록은 영구 상태 저장소가 아니며, 세션 전환이나 컨텍스트
  압축 시 과거 결정이 누락될 수 있다. 현재 상태가 README, 활성 플랜, history에
  분산되면 다음 세션이 우선 읽을 최신 스냅샷도 명확하지 않다.
- **해결 설계안:**
  - `.agents/STATE.md`를 둘지, 기존 `docs/plans/`의 활성 플랜을 상태 SSOT로
    유지할지 먼저 비교한다.
  - 별도 상태 파일을 채택하면 `[현재 마일스톤]`, `[직전 변경 및 핵심 결정]`,
    `[남은 작업]`, `[마지막 갱신 시각과 기준 커밋]`만 기록한다.
  - 작업 종료와 의미 단위 체크포인트에서 상태를 갱신하고, 완료된 세부 이력은
    `docs/history/`로 이동해 스냅샷이 계속 커지지 않게 한다.
  - `AGENTS.md`에는 상태 파일의 위치와 읽기 순서만 두고 상세 규칙은 공통 SSOT에
    둔다.
- **완료 조건:**
  - [ ] `STATE.md`와 기존 활성 플랜의 책임 중복 여부를 검토한다.
  - [ ] 상태 문서의 필수 필드, 최대 분량과 갱신 시점을 정의한다.
  - [ ] 새 세션이 상태 문서만으로 현재 작업과 다음 행동을 복원하는 예시를 검증한다.
  - [ ] 오래된 상태와 기준 커밋 불일치를 탐지하는 절차를 문서화한다.

## TASK-02. 에이전트 간 변경 충돌과 덮어쓰기 방지 권한 정의

- **우선순위:** 고.
- **현상:** 한 에이전트가 성능, 보안 또는 아키텍처상의 이유로 변경한 코드를 다른
  에이전트가 의도를 확인하지 않고 가독성 중심으로 되돌리거나 재작성한다.
- **원인:** 파일과 결정의 소유권, 변경 승인자, 보호해야 할 불변조건이 핸드오프에
  명시되지 않는다. 도구별 성향을 권한으로 간주하면 현재의 실행 모드·역할 기반
  규칙과도 충돌할 수 있다.
- **해결 설계안:**
  - `.agents/skills/code-authority.md` 신설 여부를 검토하되, Claude·Cursor·Copilot
    같은 도구 이름보다 Architect, Coder, Reviewer, PM 역할과 파일 소유권을
    기준으로 승인 범위를 정의한다.
  - 코어 로직, 보안 경계, 성능 민감 구간은 플랜에 결정 근거, 불변조건, 담당자와
    승인자를 기록한다.
  - 타 에이전트 변경을 수정할 때는 코드 주석을 강제하기보다 플랜의 Context Notes
    또는 커밋 메시지에 변경 이유와 검증 근거를 남긴다.
  - 병렬 쓰기는 기존 규칙대로 worktree와 브랜치로 격리하고, 최종 반영은 PM의
    diff 검토와 테스트를 통과해야 한다.
- **완료 조건:**
  - [ ] 기존 `multi-agents-orchestration.md`의 역할·무결성 규칙과 중복을 제거한다.
  - [ ] 파일 소유권, 변경 승인권과 예외 승인 절차를 정의한다.
  - [ ] 성능 최적화를 가독성 리팩터링이 되돌리는 충돌 사례로 규칙을 검증한다.
  - [ ] 근거 없는 타 에이전트 변경 덮어쓰기를 리뷰 단계에서 차단할 수 있어야 한다.

## TASK-03. 작업 도메인별 규칙·스킬 링크 선택 기능 도입

- **우선순위:** 저.
- **현상:** 프로젝트와 스킬이 늘어나면 현재 작업과 무관한 규칙까지 탐색하거나
  로드해 기본 컨텍스트와 API 사용량이 증가할 수 있다.
- **원인 가설:** 링크된 파일 수 자체가 자동 토큰 소비를 뜻하지는 않지만, 진입
  문서의 참조 범위와 에이전트의 자동 탐색 방식이 넓으면 불필요한 문서를 읽을 수
  있다. 현재 `create-symlinks.sh`의 실제 동작과 도구별 로딩 방식을 먼저 측정해야
  한다.
- **해결 설계안:**
  - `create-symlinks.sh --mode frontend|backend|infra` 형태의 선택적 링크 기능을
    검토한다.
  - 모든 모드에 공통 진입 규칙과 안전 규칙을 포함하고, 도메인별 스킬과 설정만
    선택적으로 배포한다.
  - 알 수 없는 모드, 중복 링크, 기존 일반 파일과의 충돌, 모드 전환 시 오래된
    링크 정리 동작을 명시한다.
  - 변경 전후 동일 작업의 로드 파일 목록과 입력 토큰을 측정해 효과를 확인한다.
- **완료 조건:**
  - [ ] 현재 링크 구조와 도구별 자동 로딩 범위를 실측한다.
  - [ ] 지원 모드와 각 모드의 파일 매핑표를 정의한다.
  - [ ] 기본 모드의 기존 동작 호환성과 반복 실행의 멱등성을 검증한다.
  - [ ] 대표 작업에서 베이스 입력 토큰 30% 이상 절감 여부를 측정하고, 미달하면
    목표치나 설계를 근거와 함께 조정한다.

## TASK-04. 에이전트별 MCP·도구 설정 원본과 배포 구조 표준화

- **우선순위:** 중.
- **현상:** 새 AI 도구나 로컬 LLM CLI를 추가할 때 MCP 설정, 엔드포인트와 도구별
  설정 파일이 프로젝트 루트와 숨김 디렉터리에 흩어져 변경 추적과 재사용이 어렵다.
- **원인:** 공통 행동 규칙과 도구 실행 설정의 관리 레이어, 원본 위치와 배포
  책임이 명확히 분리되어 있지 않다.
- **해결 설계안:**
  - `.agents/configs/`를 설정 원본 디렉터리로 두고 도구별 공개 설정 템플릿과
    대상 경로 매핑을 관리한다.
  - `create-symlinks.sh`가 `.cursor/`, `.anthropic/` 등 실제 도구 요구 경로로
    설정을 링크하도록 확장한다.
  - API 키, 토큰, 개인별 절대 경로는 원본에 저장하지 않고 환경 변수 또는
    Git에서 제외한 로컬 오버라이드로 분리한다.
  - 도구별 설정 스키마와 링크 지원 여부가 다르므로 링크 불가 설정은 복사·생성
    전략과 갱신 책임을 별도로 정의한다.
- **완료 조건:**
  - [ ] 지원할 에이전트와 각 설정 파일의 원본·대상 경로 매핑표를 작성한다.
  - [ ] 비밀정보와 개인별 설정의 저장·제외 정책을 정의한다.
  - [ ] 신규 설치, 반복 실행, 깨진 링크 복구와 기존 파일 충돌을 검증한다.
  - [ ] 최소 두 종류의 도구에서 MCP 설정이 정상 로드되는지 확인한다.
